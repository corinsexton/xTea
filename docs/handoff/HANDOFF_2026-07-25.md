### Three things about this graft to not re-derive

1. **The ONNX model is NOT a re-serialisation of DF21.** It is the sklearn
   `RandomForestClassifier(n_estimators=20)` exported to ONNX — a different model family from the
   deep-forest cascade. **Measured delta:** on 29 real chr1 sites, DF21 vs ONNX agree **27/29**.
   The two disagreements (chr1:81058430, chr1:232452014) are both DF21 `1/1` → ONNX `0/1` — pure
   zygosity, no call gained or lost. The feature contract is unchanged (arff attribute blocks diff
   clean: same 15 features, same order).
   This does not move the germline bar: `tests/utils/concordance.py:4` states outright that
   genotype/quality are NOT required to match — the gate keys on position ±25 bp + MEI type.
2. **cli's `predict_for_site_onnx` has a real bug, fixed here.** It builds `SessionOptions` with
   `intra_op_num_threads = 1` / `inter_op_num_threads = 1` and then **never passes it** to
   `InferenceSession`. onnxruntime therefore sizes its pools to the core count — 96 on an O2
   compute node — and every worker fails `pthread_setaffinity_np` inside the Slurm cgroup. A single
   3-row inference emitted **93 error lines**. With `sess_options=` passed: 0 errors, 500
   predictions in 0.05 s. (cli's `train_model` also calls `ort.SessionOptions()` while importing
   `onnxruntime as rt` — a dormant NameError. Not carried over.)
3. **Both heavy imports are lazy, deliberately.** `onnxruntime` is imported inside
   `predict_for_site_onnx` and sklearn/skl2onnx inside `train_model`, so merely importing this
   module — which `x_TEA_main` does unconditionally, for every step — needs neither. Verified: the
   production py3.8 env imports `x_TEA_main` cleanly **without onnxruntime installed**.

### The germline consequence — RESOLVED, by fixing xtea2 instead

Genotype is on the critical path to the final VCF (`genotype` → `gVCF`), so germline runs need
onnxruntime in whichever env runs them. The legacy production `xTea` env cannot simply have it:
every onnxruntime requires `numpy>=1.21` and that env has **numpy 1.19.5**, so the pip plan there
was `numpy 1.19.5 → 1.24.4` — changing the env that produced every golden baseline.

**That upgrade was NOT done, and is no longer needed.** The resolution was to complete `xtea2`
(py3.10) instead, so it can run the whole pipeline. Verified, not assumed:
- all **58** modules under `xtea/` import cleanly with `~/.local` disabled;
- `run_xtea.py --dry-run` over `L1,Alu,SVA` plans 24 steps, exit 0, genotype step pointing at the
  ONNX model;
- `--gntp_classify` run for real through `x_TEA_main.py` on 29 chr1 sites: exit 0, zero stderr.

`xTea` (py3.8, numpy 1.19.5) is left **untouched** — deliberately, since it is the provenance of
every golden. It can still run everything except genotyping. A short-lived clone
(`xTea_onnx_probe`) made to trial the numpy upgrade was removed once this path was chosen; `conda
env list` should show only `xTea` and `xtea2`.

CC.3 needed no decision either way: case-control skips genotyping outright
(`run_xtea.py:361-365`), which is why `48774776` could be submitted immediately.

Verification that matters: `PYTHONNOUSERSITE=1 pytest` → **51 passed, 9 skipped**, identical to a

## What was wrong with CC.3 (morning session)

Full analysis lives in `CASE_CONTROL_PLAN.md`'s "CC.3 results" section — read that, not this.
Compressed:

- CC.3 job `48275513` had completed unexamined. It does **not** pass: L1 2/2 (field-identical) +
  1 extra (chr6:82922665, already known to be master's own baseline), SVA 0/0, **Alu 0/2**.
- Not a case-control bug. Alu's clip step finds both targets; the **disc step** drops them.
  Germline Alu exact-position concordance vs master is 96.6% (1073/1111), both targets among the
  38 master-only calls.
- **Bug 1 (purity):** `run_xtea.py` derived `disc_cutoff` from raw coverage, missing
  `f_cov *= f_purity` (`x_TEA_main.py:276`). Cutoff 5 where master uses 4; `36.6 × 0.86 = 31.48`
  closes exactly against master's logged 31.22/31.38.
- **Bug 2 (`b_tumor`):** `run_disc_from_scan` was called without `b_tumor`, so
  `disc_adapter.py:185`'s tumor branch was **dead code in every run ever done**; and
  `disc_adapter.py:204` hardcoded master's germline raw-disc half-cutoff regardless
  (`x_TEI_locator.py:516-520`: `cutoff/2` tumor vs `int(cutoff*3/4)+1` germline; at cutoff 4, 2 vs 4).
- Both err in the same direction: master's stricter germline rules applied to tumor runs. `raw_disc`
  feeds transduction, and every CC.3 L1 call is an orphan/transduction subtype, as are both missing
  Alu targets.

**Generalizable lesson:** the scan path bypasses master's `automatic_gnrt_parameters` entirely, so
*every* tumor/purity/coverage-gated decision must be handed over explicitly. CC.0's gate could not
have caught bug 1 — it compared xTea2-vs-xTea2 at purity 1.0, where "scaling never applied" and
"scaling correctly a no-op" look identical. Any purity gate needs master-vs-xTea2, or two purities.

Germline regression confirmed unmoved (both fixes are `opt.tumor`-gated): chr1 scan gate is
numerically identical pre/post — cutoff 5, L1 89 / Alu 469 / SVA 134 disc pass counts, 29/30
concordance, same single missed call (chr1:104688481 ALU). Note that gate *asserts ≥ 1.0* and so
reports FAILED at 0.9667 — that is its pre-existing state, not a regression.
