### Three things about this graft to not re-derive

1. **The ONNX model is NOT a re-serialisation of DF21.** It is the sklearn
   `RandomForestClassifier(n_estimators=20)` exported to ONNX — a different model family from the
   deep-forest cascade. **Measured delta:** on 29 real chr1 sites, DF21 vs ONNX agree **27/29**.
   The two disagreements (chr1:81058430, chr1:232452014) are both DF21 `1/1` → ONNX `0/1` — pure
   zygosity, no call gained or lost. The feature contract is unchanged (arff attribute blocks diff
   clean: same 15 features, same order).
   This does not move the germline bar: `tests/utils/concordance.py:4` states outright that
   genotype/quality are NOT required to match — the gate keys on position ±25 bp + MEI type.
2. **cli's `predict_for_site_onnx` has a real bug, fixed here.** It builds `SessionOptions` with
   `intra_op_num_threads = 1` / `inter_op_num_threads = 1` and then **never passes it** to
   `InferenceSession`. onnxruntime therefore sizes its pools to the core count — 96 on an O2
   compute node — and every worker fails `pthread_setaffinity_np` inside the Slurm cgroup. A single
   3-row inference emitted **93 error lines**. With `sess_options=` passed: 0 errors, 500
   predictions in 0.05 s. (cli's `train_model` also calls `ort.SessionOptions()` while importing
   `onnxruntime as rt` — a dormant NameError. Not carried over.)
3. **Both heavy imports are lazy, deliberately.** `onnxruntime` is imported inside
   `predict_for_site_onnx` and sklearn/skl2onnx inside `train_model`, so merely importing this
   module — which `x_TEA_main` does unconditionally, for every step — needs neither. Verified: the
   production py3.8 env imports `x_TEA_main` cleanly **without onnxruntime installed**.

## Accepted: one annotation-level difference at chr1:36750194

The new gate diffs cols 1-8 (everything except FORMAT/sample) against the pre-swap reference. Exactly
one call differs, and it is **accepted, not open**:

| field | new binary | old binary |
|---|---|---|
| `SVLEN` | 234 | 269 |
| `LC_CLUSTER` | 281:285 | 317:320 |

Both shift ~35 bp, so it is one underlying change in where the left-clip cluster lands on the
consensus, propagating into the inferred insertion length. **Impact is bounded: no call gained or
lost, per-type counts unchanged, concordance identical.** Note `chr1:36750194` is at 36.7 Mb, i.e.
*outside* the chr1:1M-11M window where N=1 byte-identity was checked — so that earlier claim and
this finding never contradicted each other; the position was simply never covered.

**What was established, so nobody re-derives it:**
- The interpreter and ONNX are **exonerated**: the old binary under py3.10+ONNX (`48782671`) gives
  **0** cols1-8 diffs vs the reference, genotype-only deltas at the two known sites.
- **Spill content is identical between the two binaries** — 0 diffs for both clip and anchor spills
  after normalizing order and the `<file_idx>:` tag. The spill is not the cause; the difference
  arises in the emit-from-spill stage.
- Each binary is **VCF-reproducible across two runs** (`48785477` is byte-identical to `48780156`
  in all columns).
- **But that stage has real run-to-run noise**: two runs of the *old* binary differ by 1639 sorted
  lines and 3 records in `Alu/tmp/cns/temp_clip.sam`. Record count does not even track the binary
  (old-reference 20035 == new 20035, old-control 20038). So two runs per binary cannot separate a
  swap-induced change from that noise, and the one-call difference sits at the noise floor.

Decision: **accepted and documented.** The gate script now subtracts this one position and reports
`known-accepted` vs `unexplained`, printing GREEN when it is the only cols1-8 difference — so a
future run neither re-investigates it nor hides a genuinely new diff behind it. If it ever needs
settling, the test is 3-5 repeats per binary to see whether 234-vs-269 is stable per binary.

## cns spill is not byte-stable (pre-existing, now documented)

`ConcFile::append` (`xtea_scan.cpp`) writes under a mutex in **tile-completion order**, so every
file written through it — the cns spill files in particular — has a run-to-run nondeterministic
line order. Content is stable (identical after sorting); byte order is not. Two consequences:

1. **Never use a spill file as a byte-comparison baseline.** The afternoon's claim that spill-path
   records "stay byte-identical" is not checkable at the spill level, because there is no
   byte-stable baseline to compare against.
2. **This order does not reach the VCF** — verified, not assumed: two runs whose spill order
   differed produced byte-identical per-type VCFs.

Documented at the source in `ConcFile`'s class comment, which is where someone would trip on it.

## Test harness

- **New (evening): `tests/test_scan_multifile.py`, 10 tests, ~11 s.** The multi-BAM plan's
  verification items 2 and 3 (`HANDOFF_2026-07-21.md:160-175`) had **no coverage at all** — only N=1
  byte-equality had ever been checked, which is precisely the case that cannot exercise pooling.
  Pooling exactness: split one window's reads across two files, scan together, require the
  clip-site table and per-read streams to equal the unsplit scan. **The split is by read name, not
  by region** — a region split would break the "mates never span files" precondition the engine's
  per-file state relies on, so it would measure the test's own construction error instead of the
  pooling; `test_split_construction_is_sound` asserts that precondition separately. The per-read
  comparison is over **sorted lines, not sets**, because a set comparison treats a record emitted
  once per input file as equal to one emitted once — i.e. it passes straight through the
  duplicate-emission bug pooling is most likely to introduce. Also asserted: no read name leaks the
  internal `<file_idx>:<qname>` spill tag (invisible to record counts, so nothing else catches it),
  and all three `@SQ` mismatch modes (count, name/order, length) exit non-zero **naming the
  offending file** — over five pooled CRAMs from two centers, a bare "header mismatch" is not
  actionable. Validated as more than green: against the pre-multi-file binary, 7 of 9 then-existing
  tests fail. Suite totals reconcile exactly — 70 passed / 1 skipped with `XTEA2_SCAN_BIN` set,

- **New: `tests/test_rg_consistency.py`, 15 tests, 1.4 s, no external data.** Gates the multi-file

## Tooling trap: `grep` here is `ugrep`
`grep` on this machine is **ugrep**, which does **not** honour BRE `\|` alternation the way GNU grep
does — `grep -n "foo\|bar" file` returns **empty**, silently, rather than erroring. This produced a
wrong conclusion this session ("`strip_file_tag` is never called" — it is, at `cns_emit.hpp:667` and
`:975`). **An empty grep result here is not evidence of absence.** Use `grep -E "foo|bar"`, or
`grep -rn` with a single pattern. ugrep also rejects some patterns outright with
`error at position N ... empty (sub)expression`, which at least fails loudly.
