## What was wrong (the substance of this session)

Full analysis lives in `CASE_CONTROL_PLAN.md`'s "CC.3 results" section — read that, not this.
Compressed:

- CC.3 job `48275513` had completed unexamined. It does **not** pass: L1 2/2 (field-identical) +
  1 extra (chr6:82922665, already known to be master's own baseline), SVA 0/0, **Alu 0/2**.
- Not a case-control bug. Alu's clip step finds both targets; the **disc step** drops them.
  Germline Alu exact-position concordance vs master is 96.6% (1073/1111), both targets among the
  38 master-only calls.
- **Bug 1 (purity):** `run_xtea.py` derived `disc_cutoff` from raw coverage, missing
  `f_cov *= f_purity` (`x_TEA_main.py:276`). Cutoff 5 where master uses 4; `36.6 × 0.86 = 31.48`
  closes exactly against master's logged 31.22/31.38.
- **Bug 2 (`b_tumor`), found by a follow-up audit:** `run_disc_from_scan` was called without
  `b_tumor`, so `disc_adapter.py:185`'s tumor branch was **dead code in every run ever done**; and
  `disc_adapter.py:204` hardcoded master's germline raw-disc half-cutoff regardless
  (`x_TEI_locator.py:516-520`: `cutoff/2` tumor vs `int(cutoff*3/4)+1` germline; at cutoff 4, 2 vs 4).
- Both err in the same direction: master's stricter germline rules applied to tumor runs. `raw_disc`
  feeds transduction, and every CC.3 L1 call is an orphan/transduction subtype, as are both missing
  Alu targets.

**Generalizable lesson, worth applying to future gates:** the scan path bypasses master's
`automatic_gnrt_parameters` entirely, so *every* tumor/purity/coverage-gated decision must be handed
over explicitly. CC.0's gate could not have caught bug 1 — it compared xTea2-vs-xTea2 at purity 1.0,
where "scaling never applied" and "scaling correctly a no-op" look identical. Any purity gate needs
master-vs-xTea2, or two different purities.

Germline regression confirmed unmoved (both fixes are `opt.tumor`-gated): chr1 scan gate is
numerically identical pre/post — cutoff 5, L1 89 / Alu 469 / SVA 134 disc pass counts, 29/30
concordance, same single missed call (chr1:104688481 ALU). Note that gate *asserts ≥ 1.0* and so
reports FAILED at 0.9667 — that is its pre-existing state, not a regression.

  documented cross-file duplicate limitation.

**Correction to the 2026-07-21 plan, don't re-derive it:** that plan justified per-file map scoping
with "mates never span files." True for `emit_cns`/`emit_cns_multi`, but **not** for
`emit_cns_from_spill` — it has no BAM pass of its own, so its `anchors` map comes from the pooled
spill with no file identity and spans all files by construction. Fixed at the source:
`collect_cns_read` tags spilled anchor qnames `<file_idx>:<qname>` (`scan_tile` threads the index),
stripped at emit time so records stay byte-identical.

## Gate-script hygiene (bit us twice this session)
`a2_validate_chr1_cnsemit.sh` showed FAILED with the pipeline entirely fine, and this time it
**hid a result** — the concordance gate never ran. Two causes, both fixed in that script: it globbed
per-type VCFs at the pre-move-A.2 location (they now live in `merged/` with family names
`*_ALU.vcf`/`*_LINE1.vcf`), and `[ -n "$f" ] && echo ...` as a loop's last statement makes the loop
exit non-zero under `set -e`. **The pinned "check the log, not `sacct`" advice is no longer
sufficient — reporting blocks need an explicit `set +e` fence.** The new CC.3 script has one.
