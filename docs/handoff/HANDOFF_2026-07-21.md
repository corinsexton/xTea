session did the full read-and-design pass; the design is solid and doesn't need to be
re-derived, just typed in. In order:

1. **`Options.bam` (string) → `Options.bams` (`vector<string>`)** in `xtea_scan.cpp`. The
   `case 'b':` getopt branch (line ~433) splits `optarg` on whitespace into `o.bams`. Add a
   `validate_headers(const std::vector<std::string>&, const std::string& reference)` function
   (open each file, compare `sam_hdr_nref`/`sam_hdr_tid2name`/length against file 0, fail loud
   naming the exact file+discrepancy), called once in `main()` right after option parsing,
   before `build_tiles(hdr0.get(), ...)` (line ~468). `open_private(const Options&, ...)`
   (line 381) generalizes to a free `open_one(path, reference, fp, idx, hdr)`; keep a thin
   `open_private(o, ...)` wrapper over `o.bams[0]` where only one file is genuinely needed.

2. **Primary scan mode worker loop** (`main()`, lines ~608-621): `hdr0`/tiles still come from
   `o.bams[0]` only (safe once headers are validated identical). The worker lambda opens
   **one private handle per input file** (not one), and for each tile calls `scan_tile()`
   once per file, accumulating into the **same** `results[i]` `TileResult` — this is a
   flat sum across files and needs ZERO changes to `scan_tile()` itself or to the
   `(tid,pos)`-keyed aggregation maps (`clip_agg`/`disc_agg`/`clip_matein`) — those have no
   qname involved at all, so there's no collision risk in this mode regardless of file count.
   `clip_recs`/`disc_recs` (only the opt-in `--out` dump) are plain vectors — safe to
   concatenate across files too.

3. **`cns_emit.hpp`'s three functions** (`emit_cns`, `emit_cns_multi`, `emit_cns_from_spill`)
   — signatures change from `const std::string& bam` to `const std::vector<std::string>&
   bams`. **Refinement found this session (better than the plan's literal wording, same
   guarantee):** rather than prefixing qname keys with a file index in a SHARED map, it's
   simpler and equally airtight to make the qname-keyed state (`disc_needs` in `emit_cns`;
   `anchors`/`mate_seq` in the other two) **fresh/local to each file's own loop iteration**,
   since a read's mate is always in the same physical file — so pass 1 (build the map) and
   pass 2 (resolve mates) for one file always run back-to-back before moving to the next
   file, and the map for file N+1 never coexists with file N's. This eliminates the
   collision risk structurally with LESS code churn than key-prefixing (no need to touch the
   final per-type/per-candidate fan-out logic's key format, just re-scope where the map is
   declared). **Concretely for `emit_cns_multi`/`emit_cns_from_spill`:** since their fan-out
   step (per MEI type) needs the pooled, RESOLVED anchor+mate-seq data after all files are
   processed, `HeldAnchor` needs two new fields added (`qname`, `s_mate_first` — currently
   implicit via the map key) plus a `mate_seq` field (currently a separate `mate_seq` map);
   pass 2 for each file mutates `.mate_seq` directly on that file's own local `anchors_local`
   map's entries (guarding "first resolved wins" with a local `resolved` set, matching
   today's exact semantics), then only entries with a non-empty `mate_seq` get flattened
   into a pooled `anchors_all` vector for the final per-type fan-out (which iterates a flat
   vector now, not a map — mechanical rewrite of lines ~646/931 in `cns_emit.hpp`). `clips`
   (`vector<HeldClip>`) and `lowq` maps pool trivially across files with no changes (already
   positional, no qname). Was mid-read of `emit_cns_from_spill` (the ACTIVELY used one, via
   `run_xtea.py`'s `--cns-emit-scan` fan command) when interrupted — full body already read
   this session, in-context understanding is solid, just needs to be typed following the same
   pattern as `emit_cns`/`emit_cns_multi`.

4. **`gather_tile`'s Part-2 mode** (`xtea_scan.cpp` `--disc-pos-in`/`--mate-fastq`, lines
