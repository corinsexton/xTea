## What shipped this session (committed + validated)
**Phase C move A.1 — locus-keyed type resolution (`381f41f`).** Replaced the `SampleVCFMerger` call in
`run_xtea.py` (per-type VCFs → one merged VCF) with a first-class `LocusTable`
(`xtea/locus_table.py`: `Locus`, `LocusTable.assign_type()`, `write_merged_vcf()`). Re-expresses the
pinned rule from `docs/handoff/MOVE_A_PLAN.md`: types load in priority order L1→SVA→Alu (HERV unused),
a call within ±50bp of an already-placed call is the same locus, the placed call is kept UNLESS the
incoming call carries `two_side_tprt_both` and the placed one does not (no numeric QUAL comparison —
confirmed dead code in master too). `run_xtea.py`'s `produced_vcfs` changed from a list to a
`{type: path}` dict so the merge step knows which VCF belongs to which type.

**🐛 BUG FOUND + FIXED mid-implementation: B5, master's `SampleVCFMerger` conflict resolution
(documented `docs/clipdisc_contract_spec.md` §4).** While building A.1, direct execution of the real
`x_vcf_merger.SampleVCFMerger.merge_single_sample_ins` revealed it keys every locus by its own exact
VCF position in ONE dict. `cmp_quality_of_two_ins` decides `b_keep_first`, but the code only
`continue`s on the override branch (`b_keep_first==False`); the "keep existing" branch
(`b_keep_first==True`) falls through to an unconditional dict write of the INCOMING (losing) record
anyway. Effect: (a) conflicting calls at **different** positions — both survive (a spurious duplicate
locus); verified via a synthetic repro (fake L1 + non-TPRT Alu 10bp apart → both appear in the merged
output). (b) conflicting calls at the **exact same** position — the fallthrough write lands on the same
dict key, silently overwriting the "kept" entry, so whichever type loaded LAST (always Alu, load order
L1→SVA→Alu) wins regardless of priority or TPRT. Verified against the real WGS seeded merged golden
(`master_golden_wgs_seeded/NA12878/NA12878.wgs.merged.golden.vcf`, 1529 calls): **all 5 of its
non-TPRT-override conflicts are exact-position ties, and all 5 wrongly resolve to Alu** instead of the
intended L1/SVA priority winner (chr1:241980544, chr3:110694547, chr5:142000088, chr12:99387860,
chr17:33737479). This merger is not part of master's own `-f 5907` pipeline (which stops at per-type
VCFs) — it's code xTea2 reuses for its single-VCF deliverable — so there was no "reproduce master"
obligation, only a real correctness bug not worth carrying forward. **User decision: fix it now**
(deviates from strict byte-identity with the old buggy merged golden, at exactly those 5 loci).

**Fix + validation.** `LocusTable` keeps each chromosome's placed loci in a **list** (not a
position-keyed dict), so a resolved conflict always replaces-or-drops the loser in place — no
collision, no duplicate, independent of whether the two positions happen to be equal. Re-running the
corrected rule over the WGS seeded per-type goldens reproduces the old 1529-call merged golden
**byte-for-byte except at those 5 loci**, which now resolve to the correct L1/SVA priority winner
(independently confirmed against `docs/handoff/conflict_analysis.py`'s list-based simulation, which
never had the bug — it matches the new output exactly). chr1 (30 calls, no conflicts there hit the bug)
is byte-identical, old vs new. New `tests/test_locus_table.py` (6 tests: no-conflict passthrough,
load-order priority without TPRT, TPRT override, the B5 exact-tie regression case, out-of-window
non-conflict, header/sort behavior of `write_merged_vcf`). Full pytest suite green (37 passed, 9 skipped
— skips are all `XTEA2_SCAN_BIN`/`XTEA2_OUTPUT_DIR` env-gated, expected without a live run).
