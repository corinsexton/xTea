## Mosaic mode — plan drafted this session (`docs/handoff/MOSAIC_PLAN.md`, NOT YET COMMITTED)

User's ask: start planning mosaic MEI calling, with an explicit priority — **speed at very high
coverage (300x) matters more than replicating master's algorithm structure exactly** ("prohibitively
slow on 300x data... okay if memory scales up... avoid intermediate files and exorbitant runtimes...
can give many cores"). This reframes the whole plan relative to how case/control was approached (there,
matching master's exact command shape was the point; here, going straight to a fast design is).

Two research passes (forked) + direct verification pinned:
- **Mosaic is single-sample; earlier "multi-sample joint-calling orchestration" concern was too
  pessimistic.** `--joint` (`x_joint_calling.py`) is a separate, optional, post-hoc singleton filter
  across independently-run per-sample results — not a joint caller, no per-sample read-level
  comparison. Deferred to M.4, lowest priority, doesn't block anything.
- **The real 300x bottleneck, corrected from the first research pass's framing:** it's NOT that the
  mosaic polyA check itself is expensive computation (`"AAAAA" in seq` is trivial) — it's that mosaic's
  clip step still runs master's original per-read Python loop (`clip_read.py`), the exact same root cost
  `xtea-scan`'s C++ rewrite already solved for germline clip detection. Mosaic just hasn't been ported
  into that engine yet, and needs one extra cheap per-read fact (polyA membership) that `xtea-scan`
  doesn't currently expose. Disc step is already shared with case-control's `--somatic` disc (only
  difference: `PEAK_WINDOW` 100→30bp); mosaic post-filtering is pure in-memory record filtering, zero
  BAM re-reads, doesn't scale with coverage. So the ONE real target is the clip step.
- **A related general finding, found while chasing this (not mosaic-specific):** the plain germline
  clip step (`clip_read.py:collect_clipped_parts_by_chrm`) ALSO does a polyA check today (a different,
  min-count one, narrow 7-8bp band) — and it's confirmed **absent from `xtea-scan.cpp`/`scan_adapter.py`
  entirely** (direct grep, zero hits). So the C++ work should generalize polyA support for BOTH the
  existing germline min-count filter AND mosaic's substring-tally, closing a real (if narrow, likely
  small-impact) existing gap in the already-shipped fast path, not just adding a mosaic-only feature.
- **User also asked whether TSD (target site duplication) has the same kind of inefficiency — checked,
  no.** `x_TSD.py:get_TSD_seqs` is a 60-line module called once per FINAL call (from `x_gvcf.py`, at
  gVCF-writing time), one reference-FASTA lookup per surviving call, O(#final calls), zero BAM access.
  Not a target. (`TSD=NULL` seen in CC.3's example VCF rows is a call-type characteristic — set
  explicitly for records lacking two-sided clip positions, e.g. the "orphan_or_sibling_transduction"
  calls we happened to be looking at — not a bug or a skipped computation.)
- **No real executed mosaic run found on disk** (searched broadly — unlike case/control's free LFS
  2921/L1 gate). Validation plan: generate our own golden by running master's own `--mosaic` pipeline
